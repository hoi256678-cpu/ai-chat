# 위기 감지 경계 오탐 줄이기: Kiwi 형태소 분석 설계

> 작성: 2026-11-18. 로드맵 A(위기 신호 감지)의 후속 작업이다. 학습 기록 `docs/study/algorithm-study-log.md` §11, §13과 이어진다.

## 배경

`lib/crisisDetection.ts`의 `crisisLevel()`은 원문에 위기 키워드가 그대로 있으면 `direct`로 판정하고, 이때는 AI 판단과 상관없이 109 안내 띠를 항상 띄운다. 키워드를 글자 단위로 비교하기 때문에 "어제 축구에서 자살골 넣었어"처럼 키워드가 다른 단어의 일부로 들어간 문장도 `direct`가 된다(경계 오탐).

학습 기록 §11에서 정리한 방법 네 가지 중 ④ 형태소 분석은 "정확하지만 무겁고 직접 구현 범위를 벗어남"으로 미뤄 두었다. 이번에는 검증된 형태소 분석기(Kiwi)를 가져다 쓰고, 그 결과로 판정을 바꾸는 규칙은 직접 작성한다.

## 목표와 성공 기준

- 키워드가 합성어나 다른 단어의 일부로 쓰인 문장은 109 안내를 무조건 띄우지 않고 Gemini의 문맥 판단에 맡긴다.
- 실제 위기 표현(원문에 그대로 쓴 것)은 지금처럼 항상 안내한다. **미탐을 늘리지 않는 것이 오탐을 줄이는 것보다 우선이다.**
- 성공 기준:
  - 기존 47문장 평가(`lib/crisisEval.data.ts`)에서 그대로 쓴 위기 표현 8/8 `direct` 유지 (미탐 0)
  - 새로 넣는 경계 오탐 문장(자살골 등)이 `direct`에서 `normalized`로 바뀜
  - 일상 문장 오탐 0 유지
  - Vercel 배포 환경에서 동작하고, 채팅 응답이 눈에 띄게 느려지지 않음

## 실험으로 확인한 것 (2026-11-18, 버린 코드)

- 패키지: `kiwi-nlp` 0.24.1 (Kiwi의 WebAssembly 빌드, Apache-2.0). 모델: 공식 릴리스 `kiwi_model_v0.24.1_base.tgz` (풀면 약 104MB, `cong.mdl` 76MB).
- 맥 Node: 모델 준비 0.55~1.2초, 메모리 약 850MB~1GB, 문장당 분석 약 0.18ms.
- Vercel 미리보기(무료 요금제, iad1): 빌드·배포 성공. **첫 요청 약 4.9초**(파일 읽기 1.2초 + 모델 준비 3.6초), 두 번째부터 0초, 메모리 약 860MB, 문장당 0.7~1.8ms.
- 분석 결과 (`형태/품사@어절번호`):

| 문장 | Kiwi 결과 | 의미 |
|---|---|---|
| 어제 축구에서 자살골 넣었어 | 자살/NNG@2 골/NNG@2 | 합성 명사를 쪼갠다. "자살" 토큰이 있다는 것만으로는 오탐을 못 거른다 |
| 자살충동이 들어 | 자살/NNG@0 충동/NNG@0 | 합성어지만 실제 위기일 수 있다 |
| 아자살자 | 아/IC@0 자살자/NNG@0 | "자살"과 다른 토큰 |
| 나 자살하고 싶어 | 자살/NNG@1 하/XSV@1 | 혼자 쓰인 명사 + 접미사 |
| 의자 살까 | 의자/NNG 사/VV ᆯ까/EF | "사다"로 정확히 분석 |
| 자살 예방 캠페인 포스터 만들었어 | 자살/NNG 예방/NNG … | 다른 어절이라 독립어로 남는다. **이번 작업으로 해결되지 않는다** |

- 빌드 서버에서 `/tmp`가 다른 디스크라 `rename()`이 실패(EXDEV)했다. 모델은 복사로 옮긴다.

## 판정 규칙 (직접 작성 대상)

원문 판정이 `direct`이고 걸린 키워드가 명사 키워드("자살", "자해")일 때만 Kiwi로 다시 본다. 다른 키워드("죽고 싶", "살기 싫" 등 구절)는 지금 규칙 그대로다.

| Kiwi 분석 결과 | 최종 판정 | 예시 |
|---|---|---|
| 키워드와 형태가 같은 명사 토큰이 있고, 같은 어절에서 바로 뒤에 다른 명사(NN*)가 붙지 않음 | `direct` 유지 | 나 자살하고 싶어, 자해했어 |
| 키워드 토큰 바로 뒤에 같은 어절의 명사가 붙음 (합성어) | `normalized` | 자살골, 자살충동 |
| 키워드와 형태가 같은 토큰이 없음 (다른 단어의 일부) | `normalized` | 아자살자 |
| Kiwi 로딩 실패, 시간 초과, 오류 | `direct` 유지 (지금과 같음) | — |

- 한 문장에 키워드가 여러 번 나오면 하나라도 `direct` 조건을 만족하면 `direct`다.
- `normalized`로 낮춰도 Gemini가 응답 형식(JSON의 crisis 칸)으로 위기 여부를 판단하므로, "자살충동"처럼 합성어지만 실제 위기인 경우는 Gemini가 잡는다(기존 측정: 쪼갠 위기 표현 8/8 안내).

## 구조

### 1단계: 최종 판정을 저장하고, 기록 화면은 저장값을 읽는다 (동작 변화 없음)

지금 서버(`app/api/chat/route.ts`)는 `crisis`(direct면 true, normalized면 Gemini 판단)를 돌려주고, 브라우저가 이를 assistant 메시지의 `messages.crisis`에 저장한다. 그런데 화면(`lib/crisisNotice.ts`의 `crisisNoticeAfter`)은 메시지마다 `crisisLevel()`을 **브라우저에서 다시 실행**해 `direct`면 안내를 붙인다. Kiwi는 서버에서만 돌 수 있으므로, 이대로면 기록 화면에서 "자살골"에 안내가 다시 붙는다.

- `crisisNoticeAfter`는 다음 AI 답변에 저장된 `crisis` 값을 우선 쓰고, 다시 계산하는 것은 저장값이 없는 경우로 줄인다.
  - 답변 없이 끝난 사용자 메시지(오류): 지금처럼 원문 `direct`면 안내.
  - `crisis` 칸이 생기기 전(2026-11-05 이전) 저장된 메시지: 구분할 수 있으면 다시 계산, 구분할 수 없으면 저장값을 따른다(테스트 계정 데이터뿐이라 영향이 작다). 칸의 기본값·NULL 허용 여부를 구현 전에 확인한다(2026-11-18 SQL 접속 실패로 미확인).
- `supabase/schema.sql`에 `messages.crisis` 칸 정의가 없다. 실제 정의를 확인해 schema.sql에 맞춘다.
- 테스트: `lib/crisisNotice.test.ts`에 "저장값이 false면 원문이 direct여도 안내하지 않음" 등 추가. 1단계만 끝난 시점에는 서버 판정이 지금과 같으므로 화면 동작이 바뀌지 않아야 한다.

### 2단계: Kiwi 연결

- `kiwi-nlp`를 의존성에 추가하고, `scripts/fetch-kiwi-model.mjs`가 `prebuild`에서 공식 릴리스 모델을 `kiwi-model/`에 받는다(이미 있으면 건너뜀, `.gitignore`). 모델을 저장소에 넣지 않는다.
- `next.config.ts`: `serverExternalPackages: ["kiwi-nlp"]`, `outputFileTracingIncludes`로 `kiwi-model/**`과 `kiwi-wasm.wasm`을 `/api/chat`에 포함.
- `lib/kiwi.ts`: `getKiwi()`가 Kiwi를 한 번만 만들어 서버 메모리에 보관한다(모듈 수준 Promise, 실패하면 다음 호출에서 다시 시도). 부가 사전 중 `loadMultiDict`는 끈다(실험에서 로딩이 빨라짐).
- **미리 준비:** 채팅방(`/chat`)에 들어오면 화면이 `GET /api/chat`을 한 번 보낸다. 결과를 기다리지 않으므로 화면 로딩과 따로 진행된다. 서버의 `GET`은 `await getKiwi()`만 하고 204를 돌려준다. 같은 라우트 파일이라야 같은 함수 인스턴스로 묶일 가능성이 높아서 별도 경로를 만들지 않는다. 사용자가 입력하는 동안(보통 5초 이상) 준비가 끝나는 것을 노린다.
  - 이전 대화 기록(`/chats`)은 1단계로 저장값만 읽으므로 Kiwi가 필요 없다.
- **안전장치(동시 실행):** 원문 판정이 명사 키워드 `direct`인데 Kiwi가 아직 준비 중이면, Gemini에게 처음부터 판단 칸을 함께 요청(`generateReplyWithCrisisJudgment`)하고 그동안 Kiwi를 기다린다. Kiwi가 `direct`를 유지하면 안내, `normalized`면 Gemini 판단을 따른다. 정해 둔 시간 안에 Kiwi가 준비되지 않으면 `direct` 유지.

### 3단계: 판정 규칙 (직접 작성)

- 위치: `lib/crisisDetection.ts` 안 새 함수(예: `refineWithMorphemes(text, tokens)`). Kiwi 객체를 직접 받지 않고 토큰 배열(`{ form, tag, wordPosition }[]`)을 받아, Kiwi 없이도 테스트할 수 있게 한다.
- Claude가 맡는 부분: 테스트(위 판정 규칙 표의 문장 + 실험에서 얻은 실제 토큰 배열), 뼈대(함수 이름과 타입), 힌트, 리뷰.
- 사용자가 직접 쓰는 부분: 함수 본문(토큰 순회, 합성어 판단, 결과 반환).

### 4단계: 측정과 배포 확인

- `lib/crisisEval.data.ts`에 경계 오탐 문장(자살골, 자살충동, 아자살자 등)을 추가하고 47문장 평가를 다시 돌린다. 결과를 학습 기록과 README 위기 감지 섹션에 남긴다.
- Vercel 미리보기에서 미리 준비가 실제로 같은 인스턴스에 남는지(채팅방 진입 5초 뒤 메시지 → Kiwi 대기 0초), 첫 요청 지연을 잰다.

## 오류 처리

- Kiwi 로딩·분석 실패는 모두 `direct` 유지로 끝난다. 사용자에게 오류를 보여 주지 않고 서버 로그만 남긴다.
- 준비 요청(`GET /api/chat`) 실패는 화면에서 무시한다.

## 한계

- "자살 예방 캠페인 포스터"처럼 키워드가 독립된 단어로 쓰인 오탐은 남는다.
- 채팅방에 들어올 때마다 약 860MB 메모리를 쓰는 인스턴스가 깨어난다. 사용자가 늘면 비용과 준비 시점(채팅방 대신 첫 입력 시작 시 등)을 다시 검토한다.
- Vercel이 준비 요청과 메시지를 다른 인스턴스로 보내면 미리 준비가 소용없다. 이때는 안전장치(동시 실행)로 최악 1~2초가 늘어난다.
- 모델을 빌드 때 GitHub 릴리스에서 받으므로, 릴리스 주소가 바뀌면 빌드가 실패한다. 버전을 고정해 두었다.
