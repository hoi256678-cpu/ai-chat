## 1. 배경과 목표

졸업작품을 AI 도움(바이브코딩) 위주로 만들어 왔지만, 면접에서 설명하려면 핵심 알고리즘을 직접 이해하고 구현해야 한다고 판단해 2026년 10월 7일부터 "직접 구현" 트랙을 시작했다.

- **졸업작품:** 의료IT공학과 졸업작품 `ai-chat`. AI 헬스케어 챗봇(상담 채팅, 증상 체크와 진료과 추천, 피부 사진 분류, 근처 병원 찾기, 복약 관리, 워치 심박수 분석)
- **지원 방향:** 헬스케어 분야 풀스택 개발. 백엔드와 AI/데이터를 중심으로 다룬다.
- **목표:** 면접에서 "문제 → 선택 이유 → 대안 → 측정 결과"를 막힘없이 설명할 수 있는 알고리즘을 졸작에 직접 넣는다.
- **역할 분담:** 코드는 본인이 직접 쓴다. AI(Claude)는 개념 설명, 확인 질문, 단계별 힌트, 코드 리뷰, 문제와 채점기 제작만 맡는다.
- **출발점:** 학교에서 알고리즘을 C로만 배웠고, 이번 주제 중 아는 것은 BFS뿐이었다.

## 2. 졸작 프로젝트 구조 이해

알고리즘을 넣기 전에 졸작이 어떤 언어와 환경으로 돌아가는지부터 정리했다. 요약하면 화면과 서버는 TypeScript 하나로, AI 모델은 Python으로, 웨어러블 연동은 Kotlin으로 되어 있다.

```
                    비밀 키가 필요한 호출만 Next.js 서버를 거친다

┌─────────────────────────┐      ┌──────────────────────────────┐      ┌──────────────────────┐
│ 브라우저 · 안드로이드 앱  │─────▶│ Next.js API 라우트  ★          │─────▶│ Gemini API           │
│ React 19 화면 (TS)       │      │ Vercel 서버리스 · TypeScript  │      │ AI 답변 생성          │
│ Capacitor로 앱 포장       │      │ 비밀 키: Gemini, Kakao REST   │      └──────────────────────┘
│ Kotlin: Health Connect   │      │ 위기 감지 (과제 A 적용 위치)   │─────▶┌──────────────────────┐
└────────────┬────────────┘      └──────────────┬───────────────┘      │ Kakao Local API       │
             │ 브라우저가 직접 호출                │                      │ 근처 병원 검색        │
             │                                   │                      └──────────────────────┘
             ▼                                   └─────────────────────▶┌──────────────────────┐
┌──────────────────────────────┐                                        │ ml-service (로컬 전용) │
│ Supabase (BaaS)              │                                        │ Python·PyTorch·FastAPI │
│ PostgreSQL DB + 로그인        │                                        │ 피부 사진 분류 (과제 C) │
│ RLS: 본인 데이터만 접근        │                                        └──────────────────────┘
│ 공개 anon 키로 직접 호출       │
└──────────────────────────────┘
```

채팅, 증상체크, 병원 검색은 Next.js 서버를 거치고, 기록 저장과 조회는 브라우저가 Supabase에 직접 한다. ★ 표시가 과제 A가 들어갈 곳이다.

### 언어 구성 (저장소 파일 기준)

| 언어 | 파일 수 | 위치 | 역할 |
| --- | --- | --- | --- |
| TypeScript (.ts) | 29 | lib/, app/api/, proxy.ts | 서버 로직, API, 유틸 함수 |
| TypeScript + JSX (.tsx) | 25 | app/\*\*/page.tsx, components/ | 화면 (React 컴포넌트) |
| Python (.py) | 10 | ml-service/ | 피부 사진 분류 모델 학습과 서빙 (PyTorch, FastAPI) |
| Kotlin (.kt) | 2 | android-shell/ | Health Connect에서 워치 심박수 읽기 |

JavaScript로 직접 쓴 기능 코드는 없다. TypeScript는 작성할 때의 언어이고, 빌드되면 JavaScript로 바뀌어 브라우저와 Node.js에서 실행된다.

### TypeScript와 컴파일러

- TypeScript는 JavaScript에 타입 검사를 더한 언어다. 타입 오류를 실행 전에 잡고, 실행 중에는 타입이 사라진다.
- 타입 검사는 tsc(Microsoft 공식), 변환은 SWC(Rust), 묶기는 Turbopack이 맡는다.
- `npm run dev`는 속도를 위해 변환만 하고, `npm run build`는 타입 검사까지 통과해야 배포된다.
- Flutter는 컴파일러가 아니라 프레임워크다. 졸작에서 같은 층은 Next.js + React이고, 앱으로 감싸는 도구는 Capacitor다.

### 백엔드는 두 개다

- **Next.js API 라우트 (직접 구현):** Gemini AI 호출, Kakao 병원 검색, 위기 감지. Vercel 서버리스 함수로 배포된다.
- **Supabase (BaaS):** PostgreSQL DB와 로그인. 브라우저가 DB에 직접 읽고 쓰며, RLS(Row Level Security)가 "본인 데이터만" 규칙을 DB 레벨에서 강제한다.

### API 키 배치

기준은 "공용 서버 vs 개인 서버"가 아니라 "브라우저에서 도는 코드냐, 서버에서 도는 코드냐"다. 브라우저로 간 것은 전부 공개된다.

| 키 | 위치 | 공개 여부 | 보호 방법 |
| --- | --- | --- | --- |
| GEMINI_API_KEY | Next.js 서버 | 비공개 | 서버에서만 사용 |
| KAKAO_REST_API_KEY | Next.js 서버 | 비공개 | 서버에서만 사용 |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | 브라우저 | 공개 (원래 공개용) | DB의 RLS 규칙 |
| NEXT_PUBLIC_KAKAO_MAP_APP_KEY | 브라우저 | 공개 (원래 공개용) | Kakao에 등록한 도메인에서만 동작 |

`NEXT_PUBLIC_` 접두사가 붙은 환경변수만 브라우저 코드에 들어간다. RLS를 무시하는 Supabase `service_role` 키는 쓰지 않는다.

## 3. 알고리즘 적용 로드맵

졸작 코드에서 "판단을 LLM이나 단순 비교에 맡기고 있는" 자리 세 곳을 찾아, A → B → C 순서로 직접 구현하기로 했다. 각 과제는 스펙 → 계획 → 구현을 따로 거친다.

| 과제 | 대상 코드 | 현재 문제 | 적용할 알고리즘 | 수준 |
| --- | --- | --- | --- | --- |
| A. 위기 신호 감지 | lib/crisisDetection.ts | 키워드 7개를 includes()로 하나씩 확인. "죽 고 싶", "주꼬싶어" 같은 변형을 놓침 | Aho-Corasick + 한글 자모 분해 + Levenshtein 거리 | 학부 심화 ~ 대회 상급 |
| B. 심박수 이상 탐지 | lib/biometrics.ts | 평균/최대/최소만 계산해 Gemini에 판단을 맡김 | 중앙값/MAD robust z-score → BOCPD (Adams & MacKay, 2007) | 대학원 |
| C. 피부 분류 신뢰도 보정 | ml-service (Python) | "확신도 60% 미만이면 참고만" 기준이 있지만 softmax 확률은 과신 경향 | Temperature Scaling + ECE (Guo et al., 2017) | 대학원 (ML) |

### A의 설계 결정: 1차 알고리즘 + 2차 AI (2026-10-07)

위기 표현의 변형은 종류가 달라 한 가지 방법으로 잡을 수 없다. 그래서 역할을 둘로 나눴다.

```
사용자 메시지
   │
   ▼ 1차: 직접 구현한 알고리즘 (lib/crisisDetection.ts)
   │   정규화(공백·특수문자 제거) → Aho-Corasick으로 직접 표현 검사
   │   걸리면 → Gemini를 부르지 않고 109 안내 메시지 즉시 응답
   │
   ▼ 2차: Gemini 문맥 판단 (lib/chatPersona.ts, 이미 있음)
       비튼 표현(주꼬싶다), 돌려 말하기, 문맥 → 위기면 같은 안내 메시지
```

| 변형 종류 | 예시 | 담당 |
| --- | --- | --- |
| 띄어쓰기, 특수문자 | 죽 고싶다, 죽.고.싶.다 | 1차 (정규화) |
| 어미 변화 | 죽고싶다, 죽고싶어, 죽고싶네 | 1차 (어간 키워드 + Aho-Corasick) |
| 오타, 일부러 비틀기 | 주꼬싶어, 죽구싶다 | 2차 (AI). 자모 분해 + 편집거리는 선택 과제 |
| 부정, 과장 | 죽고싶지 않아, 배고파 죽을 것 같아 | 2차 (AI 문맥 판단) |

- **이유:** 1차는 결정적이라 테스트할 수 있고, 빠르고, AI 서버가 장애여도 동작한다. 2차는 문맥을 이해한다. 가장 명확하고 위험한 표현은 확실하게 잡고, 애매한 표현은 AI에 맡긴다.
- **원칙:** 위기 감지에서는 놓치는 것(미탐)이 잘못 울리는 것(오탐)보다 위험하다. 다만 1차에서 걸리면 AI를 거치지 않고 바로 안내하므로, 1차 키워드는 "걸리면 무조건 안내해도 괜찮은 것"만 넣는다.
- **교체 방식:** `containsCrisisSignal()`의 이름과 입출력(문자열 → true/false)은 그대로 두고 안쪽만 바꾼다. `route.ts`는 고치지 않는다. 알고리즘 본체는 `lib/algorithms/ahoCorasick.ts`(직접 작성)에 둔다. 교체 전에 기존 키워드가 모두 감지되는 회귀 테스트를 먼저 만들고, 기존 `includes()` 방식은 속도 비교 기준으로 쓴다.

### 순서를 A → B → C로 정한 이유

- **A**는 익숙한 C와 이미 아는 BFS에서 출발한다. 논문 수준 알고리즘을 코드로 옮기는 연습이자, 안전과 직결된 기능이다.
- **B**는 확률과 통계가 더해진 대학원 수준이다.
- **C**는 ML 논문 재현이다. "정확도 91.7%보다 확률을 믿을 수 있는가가 의료에서 더 중요하다"는 주장을 뒷받침한다.
- 세 개를 합치면 "서버 쪽 CS 기본기 + 데이터/AI 응용 + 의료 도메인 안전성"을 한 프로젝트에서 보여줄 수 있다.

### A에 쓰이는 알고리즘과 난이도

| 이름 | 역할 | 시간복잡도 | 백준 체감 티어 |
| --- | --- | --- | --- |
| Trie (트라이) | 키워드를 글자 단위 트리로 저장 | 삽입/검색 O(L) | 골드 |
| BFS | 트라이에 실패 링크를 얕은 노드부터 계산 | O(m) | 실버 |
| Aho-Corasick (1975) | 키워드 여러 개를 텍스트 한 번 훑기로 동시에 찾기 | 구축 O(m), 검색 O(n + z) | 플래티넘 |
| 동적계획법 | 부분 문제를 표로 채우기 | 문제별 | 골드 하위 |
| Levenshtein 거리 (1965) | 삽입/삭제/치환 횟수로 오타와 변형 허용 | O(a × b) | 골드 중위 |
| 한글 자모 분해 | "죽" → ㅈㅜㄱ, 유니코드 수식 | 글자당 O(1) | 브론즈~실버 |

(n = 텍스트 길이, m = 키워드 총 길이, z = 찾은 개수, L = 단어 길이.) 일반 기업 코딩테스트가 실버~골드인 것에 비해 A 전체는 플래티넘 수준이다. 확장 과제인 Levenshtein Automaton(Schulz & Mihov, 2002)은 대학원 수준이다.

## 4. 학습 방식과 환경

알고리즘은 익숙한 C로 먼저 검증하고, 이후 TypeScript로 옮겨 졸작에 적용한다.

### C → TypeScript 순서를 택한 이유

C 코드를 WebAssembly로 빌드해 웹 서버에 붙이는 방법도 검토했지만, 서비스 적용은 TypeScript로 하기로 했다.

- 키워드 수십 개, 메시지 수백 자 규모에서는 JS↔WASM 경계 비용(문자열 복사, UTF-16 → UTF-8 변환)이 알고리즘 실행 시간보다 클 수 있다.
- C에서 한글(UTF-8, 글자당 3바이트)을 다루려면 디코딩부터 직접 해야 한다. TypeScript는 charCodeAt() 한 번이면 된다.
- 빌드 체인(Emscripten)이 복잡해진다.
- 대신 C 단계에서는 영어 소문자로 알고리즘 자체만 검증하고, 한글 처리는 TypeScript 단계에서 한다.
- 선택 과제로 C→WASM 버전과 TS 버전을 벤치마크해 "측정 결과를 근거로 선택했다"는 근거를 남길 수 있다.

### 개발 환경

- **도구:** VS Code + Apple clang 21 (Mac에는 Visual Studio가 없다). 같은 VS Code로 졸작 TypeScript도 작업한다. Windows PC에는 2026-10-13에 GCC 16.2(WinLibs, winget 설치)를 넣었다.
- **공부 폴더:** 저장소의 `study/`. 문제마다 번호 폴더(01-trie, 02-string-set, 03-naive-search, 04-failure-link)를 둔다. 처음에는 Mac의 `~/algorithm-study/`에서 시작했고, 다른 PC에서도 이어 가도록 저장소로 옮겼다. VS Code에서 `study/` 폴더를 따로 열어 쓴다.
- **실행 단축키:** Cmd(Windows는 Ctrl) + Shift + B로 컴파일과 실행을 한 번에 한다. 폴더에 tests/01-sample.in이 있으면 예제 입력을 자동으로 넣는다.
- **AI 자동완성 끄기:** 공부 폴더에서만 GitHub Copilot을 꺼서, 정답 코드가 자동으로 채워지지 않게 했다. 졸작 등 다른 프로젝트는 그대로다.
- **코드 출처 구분:** 바이브 코딩(AI 작성)과 직접 작성한 코드를 파일 주석, 커밋 메시지(`Code-Origin: 직접` / `바이브`), 직접 작성 목록으로 구분한다. 규칙과 목록은 `docs/study/AUTHORSHIP.md`에 있다.

### 자체 문제와 채점기

백준 온라인 저지가 서비스 점검으로 쓸 수 없어서, 같은 유형의 문제를 직접 만들어 풀었다.

- 문제마다 `PROBLEM.md`(문제, 예제, 생각해 볼 것), `tests/`(입력과 기대 출력)를 두고, `study/judge.py`(자동 채점기, Mac·Windows 공통)로 채점한다. 처음에는 Mac 전용 `judge.sh`였다.
- 채점기는 맞았습니다 / 틀렸습니다 / 시간 초과 / 메모리 초과 / 런타임 에러를 판정하고, 케이스별 실행 시간(ms)과 메모리(MB)를 보여 준다.
- 기대 출력은 C 풀이와 독립적으로 Python(집합, 정규식)으로 계산했고, 별도 참고 답안으로 채점기를 검증했다.
- 테스트에는 예제, 접두사 함정, 경계 조건, 랜덤, 최대 크기(10MB 입력) 케이스를 넣었다.

## 5. 트라이 학습과 C 구현 (01-trie)

트라이의 insert와 search를 C로 직접 구현해, 테스트 5개(함정 2개 포함)를 모두 통과했다.

### 개념 이해

- **학교에서 배운 트리와 다른 점 세 가지:** ① 노드가 값을 갖지 않고 root부터의 경로가 곧 단어다. ② 자식이 2개가 아니라 글자 종류만큼(26개)이다. ③ 같은 접두사를 공유한다.
- **손으로 그리기 연습:** cat, car, cart, dog로 트라이를 그려 노드 9개(root 포함), 깊이 3에 단어 끝 3개, 깊이 4에 1개를 맞혔다. 13글자가 노드 8개로 줄어드는 접두사 공유를 확인했다.
- **구조체 이해:** `struct TrieNode *child[26]`은 자기 참조 구조체다. 포인터가 아니면 크기가 무한대가 된다. 노드 하나는 64비트에서 약 216바이트(포인터 26개 × 8 + int 4 + 정렬 여백 4)다.
- **자식 저장 방식의 트레이드오프:** 배열 26칸(O(1), 메모리 많이 씀), 연결 리스트, 정렬 배열 + 이분 탐색, 해시맵, Double-Array Trie를 비교했다. 알파벳이 작은 학습 단계는 배열, 한글을 다루는 서비스 단계는 Map을 쓰기로 했다.
- **'\0'과 NULL의 차이:** '\0'은 문자열 끝 표시(char), NULL은 아무것도 가리키지 않는 포인터다. 문자와 비교하면 '\0', 포인터와 비교하면 NULL을 쓴다.

### 구현 과정과 시행착오

1. for문 안을 어떻게 시작할지 막혔다. 빈 트라이에 "ca"를 넣는 과정을 메모리 그림으로 따라가며 "몇 번 칸? → 비었으면 만들기 → 내려가기" 3단계로 나눠 해결했다.
2. 설명 예시의 칸 번호(2)를 코드에 그대로 썼다가, 계산한 idx로 바꾸었다.
3. 필드 이름 오타(childe)를 컴파일러 에러 메시지(`trie.c:24:28: no member named 'childe'`)를 읽고 직접 고쳤다.
4. `is_end = 1`을 반복문 밖에 두어 중간 노드(c, ca)는 0, 단어 끝만 1이 되는 것을 별도 검사로 확인했다.
5. search에서 지역 변수 범위(다른 함수의 current는 보이지 않음)를 이해했고, NULL을 만나면 바로 return 0 하도록 해 segmentation fault를 막았다.

### 결과

- `search("ca")` = 0: 경로는 있지만 is_end가 0인 함정을 `return current->is_end`로 처리했다.
- `search("cars")` = 0: 내려가다 NULL을 만나는 함정을 조기 반환으로 처리했다.
- 남은 약점: 대문자, 공백, 한글이 들어오면 배열 범위를 벗어난다. 졸작 적용 전에 입력 정규화가 필요하다.

## 6. 문제 02: 금지어 검사기와 메모리 측정

백준 14425 유형(금지어 N개, 메시지 M개, 메시지 전체가 금지어인 개수)을 트라이로 풀어 8/8을 통과했고, 최악 케이스에서 메모리 1071MB를 측정해 이론값과 대조했다.

### 시행착오

- **문자열 버퍼:** 길이가 정해지지 않은 경우를 대비하려고 일부러 배열 대신 `char *word`를 썼다가 segmentation fault가 났다. 포인터는 방을 가리키는 화살표일 뿐 방 자체가 아니라는 것, `char` / `char *` / `char[]`의 차이를 정리했다.
- **길이를 모를 때의 방법:** 고정 버퍼 + 길이 제한(`%500s`), malloc + realloc 2배 증가(분할 상환 O(1), vector와 같은 원리), getline()을 비교했다. 최대 길이 500이 주어졌고 트라이가 문자열을 저장하지 않아 버퍼를 재사용할 수 있으므로 `char word[501]`을 골랐다.
- **printf 형식 지정자:** `%d`를 `&d`로 오타 내서 "data argument not used by format string" 경고가 났다. `%`는 형식 지정자, `&`는 주소 연산자다. scanf는 값을 써 넣어야 해서 주소가 필요하고, printf는 값만 있으면 된다.
- **교훈:** 컴파일러 경고(warning)가 두 버그를 미리 알려 주고 있었다.

### 메모리 측정

| 구분 | 값 |
| --- | --- |
| 최악 입력 | 금지어 10,000개 × 각 500글자 |
| 이론값 | 노드 약 5,000,000개 × 216바이트 ≈ 1,030MB |
| 측정값 | 1071MB, 실행 시간 약 0.2초 |
| 동일 데이터를 문자열로만 저장할 때 | 약 5MB |

대부분의 노드가 자식을 1개만 쓰는데도 26칸(208바이트)을 모두 잡아서 생긴 결과다. 이 문제의 메모리 제한은 1536MB라 통과했지만, 백준 기본 제한(256MB)이었다면 메모리 초과다. 이 측정은 서비스 단계에서 배열 대신 해시맵(Map)을 쓸 근거가 된다.

### 복잡도 비교

| 해시셋 | 평균 O(L) | 중간 | "있나 없나"만 볼 때 가장 간단 |

## 7. 문제 03: 숨은 금지어 찾기 (단순한 방법)

메시지 안 어딘가에 숨은 금지어를 겹침까지 모두 세는 문제를 "모든 시작 위치에서 트라이를 따라 내려가는" O(nL) 방법으로 풀어, 여러 번 고친 끝에 9/9를 통과했다. 이 코드는 다음 단계에서 Aho-Corasick과 속도를 비교할 기준(baseline)이 된다.

### 문제 설정

- 교과서 예제: 키워드 he, she, his, hers / 텍스트 ushers → she, he, hers 3개. 겹치거나 포함되는 키워드도 각각 센다.
- 사전 질문에 답했다: ① is_end는 내려가는 도중 매번 확인해야 한다. ② 단순한 방법은 O(nL)이다. ③ "aaaaaaaaab"에서 "aaaab"를 찾으면 같은 글자를 최대 L번 다시 읽는다. 이 낭비를 없애는 것이 실패 링크다.
- 최악 케이스 정답은 9,995,050이라 int(약 21억)로 충분하다고 판단했다.

### 디버깅 과정

| 시도 | 채점 결과 | 원인 | 배운 것 |
| --- | --- | --- | --- |
| 1. 반복문 하나 + 막히면 root로 | 0/9, 런타임 에러 | root에도 없는 글자로 내려가 NULL 접근 | 한 번 훑기는 Aho-Corasick의 발상이지만, root로 돌아가면 겹치는 키워드(she/he)를 놓친다 |
| 2. else로 NULL 방어 | 1/9 | 한 번 훑기 구조 자체의 한계 | 위치 2에서 시작하는 he, hers는 시도조차 안 한다 |
| 3. search(root, word + idx) | 1/9 | idx(글자 번호)와 i(시작 위치) 혼동, search는 중간 키워드를 못 셈 | 포인터 산술 word + i = i번째부터의 문자열 |
| 4. 이중 반복문 | 0/9, 런타임 에러 | current = root 위치, word[j], NULL 확인 없음 | 시작 위치마다 root부터, break로 안쪽만 빠져나오기 |
| 5. word[i + j]로 수정 | 1/9 | 확인 후 이동 순서 | 안쪽 인덱스는 시작 위치 기준 상대값 |
| 6. 확인을 if문 위로 | 2/9 | 텍스트 끝에서 마지막 노드를 못 봄 | off-by-one, 경계 조건 버그 |
| 7. 이동 직후 확인 | 9/9 | — | 루프 불변식: "j번째 차례에 current는 j번째 글자까지 읽은 상태" |

### 핵심 교훈

- **is_end는 도착한 노드에 붙는다.** 글자는 화살표(간선)에 있고, 노드는 "지금까지 읽은 문자열"이다. 이동 전에 확인하면 한 박자 늦게 보는 셈이다.
- **"얼마나 틀렸나"를 숫자로 보면 원인이 보인다.** 최악 케이스가 정확히 100,000(시작 위치 수)만큼 모자라면 "시작 위치마다 마지막 노드 하나"를 놓친 것이고, 100만큼 모자라면 "텍스트 끝까지 간 경우"만 놓친 것이다.
- **측정:** 현재 제한(메시지 10만 자, 키워드 100자)에서는 최악 케이스도 29ms다. Aho-Corasick의 이점은 키워드가 길거나 텍스트가 커질 때 드러나므로, 다음 문제에서 더 큰 입력으로 비교한다.

## 8. 실패 링크 손으로 그리기

코드 없이 종이 위에서 실패 링크를 직접 찾고, 그 링크로 텍스트를 한 번만 훑어 겹치는 키워드까지 찾는 과정을 따라갔다. 교과서 예제(he, she, his, hers)의 실패 링크 9개를 모두 맞혔다.

### 개념 이해

- **실패 링크의 정의:** 노드가 나타내는 문자열의 꼬리(앞 글자를 떼어 낸 뒷부분) 중, root에서 출발하는 경로로 트라이에 있는 가장 긴 것. 자기 자신은 빼고, 없으면 root다.
- **간선과의 차이:** 실패 링크는 글자가 없는 포인터(`struct Node *fail`) 하나다. 따라가도 텍스트를 읽지 않고, 항상 더 짧은 문자열(위쪽)을 가리킨다.
- **두 가지 쓰임:** ① 다음 글자의 간선이 없을 때 `cur`가 실제로 점프한다(`cur = cur->fail`). ② 노드에 도착할 때마다 임시 포인터 `tmp`로 사슬을 root까지 따라가며 `is_end`를 센다. ②에서는 `cur`가 움직이지 않는다.
- **사슬 = 지금 위치에서 끝나는 꼬리들:** `ushers`에서 `"she"`에 도착하면 사슬 she → he → root에서 she와 he를 함께 찾는다. 사슬 길이는 노드마다 다르고 `is_end`가 아닌 노드도 섞여 있어서, 이 헛걸음을 줄이는 출력 링크가 필요하다는 것까지 들었다.

### 손으로 그리기 과정

| 연습 | 내 답 | 결과 | 배운 것 |
| --- | --- | --- | --- |
| 1. abc, bcd에서 `"ab"`, `"bc"` | `"bc"`, `"bcd"` | 틀림 | 더 긴 쪽을 골랐다. 꼬리는 이미 읽은 글자로만 이루어지므로 항상 더 짧다 |
| 2. 같은 문제 다시 | `"b"`, root | 맞음 | 꼬리가 root 바로 아래에서 시작하는지 확인한다 |
| 3. a, ba | 셋 다 root → `"ba"`만 `"a"`로 고침 | 맞음 | `"ba"`의 꼬리 `a`가 root 바로 아래에 있다. 그 노드가 `[a]`라서 `a`도 같이 끝난다는 것(출력)을 스스로 찾았다 |
| 4. he, she, his, hers | 7/9 (`"his"`, `"hers"`를 root로) | 고쳐서 9/9 | 한 글자만 떼고 멈추면 안 되고, 있는 게 나올 때까지 계속 뗀다 (`s`) |
| 5. `ushers` 한 번 훑기 | `"sh"`를 `"h"`로, `e`에서 he 누락, `r`에서 `"h"`로 점프 | 설명 듣고 이해 | 노드 이름은 root부터의 경로 전체다. 같은 글자 `h`라도 `"h"`와 `"sh"`는 실패 링크가 다르다 |
| 6. 변형: `s`를 키워드로 | — | 이해 | 노드가 이미 있으면 `is_end`만 바뀌고 실패 링크는 그대로다. 발견 5개 |
| 7. 변형: `e`를 키워드로 | — | 이해 | 새 노드가 생기면 실패 링크가 바뀐다(`"he"` → `[e]`). 발견 4개 |

### 핵심 교훈

- **실패 링크는 트라이 모양으로만 정해진다.** `is_end`와 무관하다. 그래서 키워드를 전부 넣어 모양을 완성한 다음에 실패 링크를 만든다.
- **움직이는 포인터와 들여다보는 포인터를 구분한다.** 출력 확인 때 `cur`를 옮기면 `shell`처럼 이어지는 키워드를 놓친다.
- 남아 있던 `ushers`의 `r`, `s` 줄과 확인 문제 `hishe`는 2026-10-13에 몸풀기로 끝냈다(다음 장).

## 9. 문제 04: BFS로 실패 링크 만들기

손으로 그리던 실패 링크를 C 코드로 옮겨, 트라이의 모든 노드에 BFS로 실패 링크를 다는 `build_fail`을 직접 구현했다. 11/11을 통과했고, 노드 약 10만 개 입력에서 176ms였다.

### 몸풀기: 손으로 마저 따라가기

- **`ushers`의 `r`, `s`:** `[she]`에서 `r`이 없어 점프한 곳을 처음엔 `[her]`라고 했다. 실패 링크는 `[he]`를 가리키고, 거기서 `r`을 다시 시도해 `[her]`로 내려간다. 점프는 글자를 읽지 않고 더 짧은 꼬리로 옮겨 가는 것뿐이다. `[hers]`의 사슬 hers → s → root에서 `[s]`는 키워드가 아니라 헛걸음이고, 이걸 건너뛰는 것이 출력 링크다. 발견: she, he, hers.
- **`hishe`:** 경로 `[h] → [hi] → [his] →(점프) [s] → [sh] → [she]`를 혼자 맞혔다. 사슬 his → s, she → he에서 his, she, he 3개를 찾았다.

### 문제 설정

- 입력: 키워드 N개(≤ 1,000, 길이 ≤ 100), 질문 Q개(≤ 100,000). 질문은 트라이 노드의 문자열이고, 그 노드의 실패 링크가 가리키는 문자열의 **길이**를 출력한다. 실패 링크는 항상 질문 문자열의 꼬리라서 길이만으로 어떤 노드인지 정해진다.
- 테스트 11개: 예제(he, she, his, hers의 노드 9개), DFS 함정(abcd, bcx, cd), 한 글자, 같은 글자 반복, 겹침, 작은 랜덤, 큰 랜덤, 깊은 사슬. 정답은 정의 그대로(꼬리를 하나씩 떼어 트라이에 있는지 확인) Python으로 따로 계산했다. 큰 입력 3개는 `tests/gen.py`로 다시 만든다.

### 개념 이해

- **왜 BFS인가 (속도가 아니라 정확성):** 처음엔 "DFS는 효율이 안 나와서"라고 답했다. 실제 이유는 자식의 실패 링크를 구할 때 부모의 실패 링크와 그 사슬(모두 더 얕은 노드)을 따라가기 때문이다. DFS로 a 가지부터 하면 abcd, bcx, cd에서 `[abcd]`를 처리할 때 `[bc]`의 실패 링크가 아직 없어 NULL을 따라가다 죽는다. BFS는 얕은 노드가 항상 먼저 처리된다.
- **build_fail은 세 문장이다:** ① 정의: 꼬리 중 트라이에 있는 가장 긴 것. ② 계산: 자식 = 부모 + 글자 하나이므로, 부모의 꼬리에 그 글자를 붙여 본다. 못 붙이면 더 짧은 꼬리로 줄여 다시 시도하고, root까지 없으면 root. ③ 순서: ②가 되려면 부모의 답이 먼저 있어야 하므로 BFS. ②는 작은 문제의 답으로 큰 문제의 답을 만드는 동적계획법과 같은 사고방식이다.
- **큐는 순서만 정한다:** 실패 링크를 잇는 것은 ②의 규칙이고, 큐는 누구 차례인지 줄 세우는 도구다. 부모를 꺼낼 때 자식의 링크를 정하므로, 부모가 없는 깊이 1 노드는 큐에 넣기 전에 직접 root로 둔다.
- **while 조건 `f != root && f->child[idx] == NULL`:** "아직 root가 아니고, 여기 아래에 내 글자가 없으면 더 짧은 꼬리로". `f->child[idx] == NULL`은 `find_node`의 "간선 없음" 검사와 같다. 긴 꼬리부터 시도하므로 처음 멈춘 곳이 가장 긴 답이다. 멈춘 이유가 "찾아서"인지 "root라서"인지 while만으로는 모르므로 뒤에 `if`로 한 번 더 확인한다. 이렇게 정확한 꼬리를 찾아야 `aaaab` 안의 `ab` 같은 겹친 키워드를 검색에서 놓치지 않는다.
- **같은 꼬리를 가진 옆 가지는 이어지지 않는다:** she와 che는 둘 다 root를 가리킨다(che는 she의 꼬리가 아니다). he가 키워드로 있으면 둘 다 `[he]`를 가리킨다. 실패 링크는 여러 개가 한 노드로 모일 수 있지만, 한 노드에서 나가는 것은 항상 하나다.
- **큐 크기 100,001:** 노드는 큐에 정확히 한 번 들어가고(부모가 하나뿐), 꺼낸 칸을 재사용하지 않으므로 크기 = root를 뺀 노드 수. `insert`는 글자당 노드를 많아야 하나 만드므로 최대 1,000 × 100 = 100,000개.
- **스택, 힙, 데이터 영역:** 포인터 10만 개(약 800KB)를 함수 지역 변수로 두면 `main`의 `int len[100001]`(400KB)과 합쳐 Windows 기본 스택 1MB를 넘는다. `static`을 붙이면 데이터 영역(BSS)에 한 번만 잡히고 0으로 초기화되며, 함수가 끝나도 값이 남는다. 이름을 쓸 수 있는 범위는 그대로 함수 안이다. 트라이 노드는 `calloc`으로 힙에 있다.
- **`continue` / `break` / `return`:** 이번 바퀴만 건너뜀 / 가장 안쪽 반복문을 빠져나감 / 함수 전체를 끝냄. 안쪽 `for`의 `continue`는 바깥 `while`의 `head++`에 영향을 주지 않는다.

### 디버깅 과정

| 시도 | 채점 결과 | 원인 | 배운 것 |
| --- | --- | --- | --- |
| 1. 길이를 `strlen(find_node(...)->child)`로 | (컴파일 전 질문) | `child`는 포인터 26개 배열이지 문자열이 아니다 | 노드에는 글자가 저장되지 않는다. 글자는 간선에만 있으므로 길이(`depth`)는 만들 때 적어 둔다 |

### 핵심 교훈

- **막힌 곳 대부분은 "무엇을 기준으로 한 값인가"였다.** 알파벳 번호 ≠ 큐 위치, 부모의 꼬리 ≠ 자식의 꼬리, 인덱스 ≠ 길이.
- **조용히 틀리는 것보다 바로 죽는 게 낫다.** 없는 노드는 `NULL`로, 아직 안 정해진 실패 링크도 `NULL`로 두면 문제가 생긴 자리에서 드러난다.
- **통과했다고 이해한 것은 아니다.** 11/11 뒤에도 "빈칸을 하나씩 채워서 나무만 이해한 느낌"이라고 느꼈다. 메모 비유(실패 링크 = 막히면 갈 곳을 적어 둔 메모, 부모 메모를 보고 적는다), 코드 한 줄마다 값을 단 실행 추적, 출력을 끼워 넣은 실제 실행(`aaaab`, `ab`에서 while 2바퀴, `ab`가 없으면 root까지 3바퀴)으로 다시 확인했다. AI가 준 부분: 문제와 테스트, 함수 뼈대, BFS 반복의 빈칸 뼈대(while 조건 포함)와 리뷰.
- 아직 남은 것: `build_fail`을 빈 화면에서 다시 짜 보기, 확인 문제 `aaaab`, `aab`에서 `[aaaab]`의 실패 링크와 while 바퀴 수.

## 10. 문제 05: 아호코라식 검색

04에서 만든 실패 링크로 메시지를 한 번만 훑으며 숨은 금지어를 모두 세는 `search`를 직접 구현했다. 1/13에서 시작해 16번 고친 끝에 13/13을 통과했다. 단순한 방법(03)이 37초 걸리는 입력을 5ms에 끝낸다.

### 문제 설정

- 03과 같은 문제(메시지 안의 금지어 총 횟수, 겹침 포함)인데 제한을 키웠다: 금지어 길이 합 ≤ 100,000(한 개 최대 10,000자), 메시지 ≤ 1,000,000자, 시간 제한 1초.
- 테스트 13개: 예제(ushers, hishe), 점프 확인(jump-to-ab), DFS 함정, 일치 없음, 메시지 전체가 키워드, 작은 랜덤, 큰 랜덤, 그리고 **10번 naive-killer**(메시지 `a` × 100만, 금지어 `a`×10000과 `a`×9999 + `b`). 정답은 키워드마다 `str.find`로 따로 세거나 공식으로 계산했다. 큰 입력 4개는 `tests/gen.py`로 다시 만든다.

### 개념 이해

- **검색은 세 단계다:** 글자마다 ① 점프(지금 노드에 그 글자 간선이 없고 root가 아니면 실패 링크로 올라감) → ② 이동(간선이 있을 때만 내려감, root에도 없으면 root에 머묾) → ③ 세기(도착한 노드에서 끝나는 키워드 수를 더함).
- **점프의 시작점이 `build_fail`과 다르다:** `build_fail`은 실패 링크가 "자기 자신을 뺀" 가장 긴 꼬리라서 `p->fail`부터 찾는다. 검색은 "지금 위치에서 다음 글자로 갈 수 있나"를 묻는 것이라 `p` 자신부터 확인한다. `p->fail`부터 시작하면 갈 수 있는데도 올라가 버려 읽은 글자를 잃고(`[s]`에서 `h` → `[sh]`가 아니라 `[h]`), root에서는 `fail`이 NULL이라 죽는다.
- **사슬 세기는 `p`의 `is_end`와 상관없이 항상:** `[ab]`는 키워드가 아니어도 그 꼬리 `[b]`는 키워드일 수 있다. 도착한 노드부터 root 직전까지 실패 링크 사슬이 "지금 위치에서 끝나는 꼬리 목록"이다. 이때 `p`는 그대로 두고 임시 포인터만 움직인다.
- **사슬의 헛걸음과 미리 계산:** 10번에서 `p`가 `[a×10000]`에 머무는 동안 사슬은 매번 약 1만 칸이고 그중 키워드는 1개뿐이다(`a×9999 + b`는 `b`로 갈라진 다른 가지라 사슬 위에 없다). 99만 글자 × 1만 칸 ≈ 100억 번. 그런데 노드마다 사슬에서 세는 개수는 메시지와 무관하게 항상 같으므로 미리 적어 둘 수 있다: `[she]`의 값 = `[she]` 자신(1) + `[he]`의 값. 실패 링크는 항상 더 얕은 노드를 가리키고 BFS는 얕은 노드를 먼저 처리하므로, `ch->fail`을 정한 직후 `ch->is_end += ch->fail->is_end` 한 줄이면 된다(04에서 배운 "왜 BFS인가"와 같은 이유). 검색의 ③은 `count += p->is_end` 한 줄이 된다.
- **복잡도:** 트라이 O(m), 실패 링크와 개수 계산 O(26m), 검색 O(n). 합쳐서 O(n + m). 점프 while이 한 글자에서 여러 번 돌 수 있어도, 이동은 글자당 깊이를 최대 1 늘리고 점프는 깊이를 최소 1 줄이므로 메시지 전체에서 점프는 n번을 넘지 못한다(분할 상환).
- **100만 자 버퍼:** `static`을 붙여 스택이 아닌 데이터 영역에 둔다. `static`만 붙이고 크기를 10001로 두면 넘친 글자가 옆 메모리를 덮어 SIGSEGV(-11) 대신 SIGBUS(-10)로 죽는다. 금지어는 `insert` 뒤에 다시 쓰지 않으므로 버퍼 하나를 같이 써도 된다.

- **비슷하게 생긴 while 두 개를 구분하기:** `build_fail`(자기 자신을 뺀 꼬리를 찾음, `p->fail`부터)과 `search`(지금 위치에서 갈 수 있나, `p`부터). 이번 세션의 런타임 에러 대부분이 여기서 나왔다.
- **"답이 얼마나 틀렸나"로 원인을 좁힌다:** 0이면 갇힘, 작으면 누락(사슬, 마지막 노드), 크면 중복. 03에서 배운 방법을 다시 썼다.
- **같은 계산이 반복되면 미리 해 둔다:** 노드마다 세는 개수가 메시지와 무관하다는 관찰 하나로 3초 넘던 게 7ms가 됐다. 순서는 BFS가 보장한다. 04의 "왜 BFS인가"가 실패 링크뿐 아니라 이 계산에도 그대로 쓰였다.
- **통과 ≠ 안전:** 8번 시도는 테스트에서 안 죽었지만 `ab` / `acb`에서 죽었다. 의심스러운 경로는 작은 입력을 직접 만들어 확인한다.
- AI가 준 부분: 문제와 테스트, 채점기, 리뷰와 단계별 힌트(세 단계 의사코드, `build_fail` while과의 차이, 미리 계산할 식과 넣을 위치). 코드는 모두 직접 썼다.
- 아직 남은 것: 점프가 왜 전체 O(n)인지 한 문장으로 직접 설명해 보기, 확인 문제 `aaaab`, `aab`에서 `[aaaab]`의 실패 링크와 while 바퀴 수.

| 정렬 배열 + 이분 탐색과 비교하면? | 이분 탐색은 비교 log N번에 문자열 비교 비용 O(L)이 곱해져 O(L log N)입니다. 트라이는 메모리를 더 쓰는 대신 속도와 접두사 검색을 얻습니다. |

| 배열 기반 트라이의 단점은? | 최악의 경우를 측정해 보니 이론값대로 약 1GB가 나왔습니다. 자식이 적은 노드가 대부분이라, 알파벳이 큰 한글 서비스에서는 해시맵 기반으로 바꾸기로 했습니다. |
| 실패 링크를 왜 BFS로 만드나요? | 속도가 아니라 정확성 때문입니다. 자식의 실패 링크는 부모의 실패 링크와 그 사슬, 즉 더 얕은 노드들의 링크를 따라가며 구합니다. BFS는 얕은 노드를 항상 먼저 처리하므로 필요한 값이 이미 있습니다. DFS로 하면 abcd, bcx, cd에서 abcd를 처리할 때 다른 가지인 bc의 링크가 아직 없어 NULL을 따라가게 됩니다. 이 예제를 테스트에 넣어 확인했습니다. |
| 왜 C로 하지 않고 TypeScript로 서비스에 넣었나요? | 입력이 짧아 WASM 경계 비용이 알고리즘 실행 시간보다 클 수 있고, 한글 처리도 TypeScript가 간단합니다. C는 알고리즘 검증용으로 썼습니다. |
| 반복문이 맞다는 걸 어떻게 확신하나요? | 루프 불변식을 정했습니다. "j번째 차례가 끝날 때 current는 j번째 글자까지 읽은 상태"라는 것을 지키도록 이동 직후에 확인해, 경계에서 놓치는 경우를 없앴습니다. |
| scanf에는 &가 필요하고 문자열 배열에는 왜 필요 없나요? | scanf는 변수에 값을 써 넣어야 해서 주소가 필요합니다. 배열 이름은 그 자체가 첫 칸의 주소로 바뀌므로 &를 붙이지 않습니다. |
| 실패 링크란 무엇인가요? | 노드가 나타내는 문자열의 꼬리 중 트라이에 있는 가장 긴 것을 가리키는 포인터입니다. 다음 글자로 갈 수 없을 때 이미 읽은 글자 중 쓸모 있는 꼬리로 점프해서, 텍스트를 다시 읽지 않고 한 번만 훑을 수 있게 해 줍니다. |
| 겹치는 키워드(she 안의 he)는 어떻게 찾나요? | 노드에 도착할 때마다 실패 링크 사슬을 따라가며 키워드 끝 표시를 확인합니다. 사슬은 지금 위치에서 끝나는 꼬리들의 목록이라 같은 위치에서 끝나는 키워드가 모두 나옵니다. 이때 현재 위치 포인터는 그대로 두고 임시 포인터로만 따라가야 이어지는 키워드를 놓치지 않습니다. |
| 키워드를 추가하면 실패 링크를 다시 만들어야 하나요? | 실패 링크는 트라이 모양으로 정해집니다. 이미 있는 노드가 키워드가 되면 그대로지만, 새 노드가 생기면 바뀔 수 있습니다(예: e를 추가하면 he의 실패 링크가 root에서 e로 바뀜). 그래서 키워드를 모두 넣은 뒤 한 번에 만듭니다. |
| 실패 링크는 어떻게 계산하나요? | 자식은 부모에 글자 하나를 붙인 것이므로, 자식의 꼬리도 부모의 꼬리에 그 글자를 붙인 것입니다. 부모의 실패 링크에서 그 글자로 내려갈 수 있으면 거기가 답이고, 없으면 더 짧은 꼬리(실패 링크의 실패 링크)로 줄여 다시 시도합니다. root까지 없으면 root입니다. 이미 구한 작은 문제의 답을 재활용하는 동적계획법과 같은 구조입니다. |
| while에서 왜 긴 꼬리부터 확인하나요? | 실패 링크는 가장 긴 꼬리여야 하기 때문입니다. 긴 것부터 줄여 가면 처음 멈춘 곳이 곧 가장 긴 답입니다. 중간을 건너뛰고 바로 root로 가면 aaaab 끝에 겹친 ab 같은 키워드를 검색에서 놓칩니다. |
| BFS 큐의 크기는 어떻게 정했나요? | 노드는 부모가 하나뿐이라 큐에 정확히 한 번 들어가고, 꺼낸 칸은 재사용하지 않으므로 크기는 노드 수면 됩니다. insert는 글자당 노드를 많아야 하나 만들어서 키워드 1,000개 × 100글자 = 최대 100,000개로 잡았습니다. |
| 스택과 힙의 차이는? | 지역 변수는 스택에 올라가 함수가 끝나면 사라지고 크기 제한이 있습니다(Windows 기본 1MB). malloc으로 받은 메모리는 힙에 있어 free할 때까지 남습니다. 큐로 쓸 포인터 10만 개(약 800KB)는 스택에 두면 넘칠 수 있어 static으로 데이터 영역에 두었습니다. static 지역 변수는 0으로 초기화되고 함수가 끝나도 값이 남습니다. |
| 아호코라식 검색은 글자마다 무엇을 하나요? | 세 단계입니다. 지금 노드에 그 글자 간선이 없으면 실패 링크로 올라가고(점프), 간선이 있으면 내려가고(없으면 root에 머묾), 도착한 노드에서 끝나는 키워드 수를 더합니다. 점프는 실패 링크를 만들 때와 달리 지금 노드 자신부터 확인합니다. 갈 수 있는데 올라가면 읽은 글자를 잃기 때문입니다. |
| 아호코라식의 시간복잡도는? | 텍스트 길이 n, 키워드 길이 합 m에 대해 O(n + m)입니다. 트라이와 실패 링크 구축이 O(m)(알파벳 크기는 상수), 검색이 O(n)입니다. 찾은 위치를 전부 출력하면 개수 k가 더해집니다. |
| 점프 while이 한 글자에서 여러 번 도는데 왜 검색이 O(n)인가요? | 현재 노드의 깊이로 설명합니다. 이동은 글자당 깊이를 최대 1 늘리고, 점프는 더 짧은 꼬리로 가므로 깊이를 최소 1 줄입니다. 깊이는 0 아래로 내려가지 않으니 전체 점프 횟수는 전체 이동 횟수(n)를 넘지 못합니다. |
| 겹치는 키워드를 셀 때 사슬을 매번 따라가면 안 되나요? | 최악의 경우 느립니다. 메시지 a 100만 자, 키워드 a×10000에서는 사슬이 매번 약 1만 칸이고 그중 키워드는 하나뿐이라 약 100억 번을 돕니다. 실제로 3초를 넘었습니다. 노드마다 끝나는 키워드 수는 텍스트와 무관하므로, 실패 링크를 만들 때 "자기 값 + 실패 링크의 값"으로 미리 더해 두면 검색은 덧셈 한 번입니다. BFS가 실패 링크 노드를 먼저 처리하므로 값이 항상 준비돼 있습니다. 7ms로 줄었습니다. |
| 단순한 방법보다 실제로 얼마나 빠른가요? | 같은 입력으로 측정했습니다. 메시지 100만 자, 키워드 1만 자인 최악 입력에서 단순한 방법은 37초, 아호코라식은 5ms였습니다. 짧은 랜덤 키워드에서는 둘 다 10ms대로 비슷했습니다. 그래서 아호코라식의 가치는 평균 속도보다 최악의 경우를 보장하는 데 있다고 봅니다. |

## 12. 자소서 활용 포인트

아래 소재는 "상황 → 행동 → 결과 → 배운 점" 순서로 정리했다. 수치는 실제로 측정한 값만 썼다.

### 소재 1. AI에 기대던 개발에서 직접 구현으로 (성장, 주도성)

- **상황:** 졸업작품을 AI 도움으로 빠르게 만들었지만, 핵심 로직을 설명할 수 없다는 한계를 느꼈다.
- **행동:** 역할을 나눠 코드는 직접 쓰고 AI는 튜터로만 썼다. 공부 폴더에서는 AI 자동완성(Copilot)을 일부러 껐다.
- **결과:** 트라이, 실패 링크 구축(BFS), 아호코라식 검색을 C로 직접 구현하고 자체 채점 문제 5개(총 46개 테스트)를 모두 통과했다. 통과한 뒤에도 이해가 단편적이라고 느껴, 실행 추적과 손 계산으로 다시 확인했다.
- **배운 점:** 도구를 쓰되 핵심은 이해하고 설명할 수 있어야 한다.

### 소재 2. 측정으로 자료구조를 선택한 경험 (문제 해결, 논리)

- **상황:** 배열 기반 트라이가 메모리를 낭비한다는 것을 이론으로만 알고 있었다.
- **행동:** 최악 입력(단어 10,000개 × 500글자)을 만들어 메모리를 직접 측정하고, 노드 수 × 216바이트 이론값과 비교했다.
- **결과:** 측정값 1071MB가 이론값 약 1,030MB와 일치했다. 같은 데이터를 문자열로만 저장하면 약 5MB다.
- **배운 점:** 글자 종류가 수천 개인 한글 서비스에서는 해시맵 기반 노드를 쓰기로 결정했다. 자료구조는 감이 아니라 측정으로 고른다.

### 소재 3. 체계적인 디버깅 (끈기, 분석력)

- **상황:** 숨은 금지어 찾기 문제에서 7번의 시도 동안 0/9에서 2/9 사이를 오갔다.
- **행동:** 한 번에 하나씩만 고치고 매번 채점했다. 케이스별로 정답과 출력의 차이를 봤다. 차이가 정확히 100,000(시작 위치 수), 다음에는 100이라는 점에서 놓친 경우를 역추적했다.
- **결과:** 원인이 "이동 전에 확인하는" off-by-one임을 찾아 9/9를 통과했다.
- **배운 점:** 루프 불변식으로 코드의 정확성을 설명하는 법, 컴파일러 경고를 무시하지 않는 습관을 얻었다.

### 소재 4. 의료 서비스의 안전성 (직무 적합성)

- **상황:** 상담 챗봇의 위기 감지가 키워드 7개의 단순 포함 검사라서, 띄어쓰기나 오타로 우회한 표현을 놓칠 수 있었다.
- **행동:** 놓치는 것(false negative)이 치명적인 기능임을 정의하고, Aho-Corasick + 한글 자모 분해 + 편집거리로 개선하는 계획을 세웠다. (진행 중)
- **확장:** 심박수 이상 탐지(BOCPD), 피부 분류 모델 신뢰도 보정(Temperature Scaling)으로 "AI의 판단을 그대로 믿지 않고 검증한다"는 일관된 스토리를 만든다.

### 소재 5. 최악의 경우를 측정해 알고리즘을 바꾼 경험 (문제 해결, 성능)

- **상황:** 아호코라식 검색을 직접 구현해 13개 중 12개 테스트를 통과했지만, 메시지 100만 자와 1만 자짜리 키워드로 만든 최악 입력에서 3초 넘게 걸렸다.
- **행동:** 원인을 계산으로 좁혔다. 글자마다 실패 링크 사슬을 약 1만 칸씩 따라가는데 그중 키워드는 하나뿐이라 약 100억 번의 헛걸음이었다. "노드마다 끝나는 키워드 수는 입력과 무관하다"는 점에서, 실패 링크를 만들 때 BFS 순서로 미리 더해 두도록 바꿨다.
- **결과:** 같은 입력이 7ms로 줄어 13/13을 통과했다. 같은 입력에서 이전에 구현한 단순한 방법은 37초가 걸렸다(5ms 대비 약 7,500배).
- **배운 점:** 평균 입력에서는 두 방법이 비슷했다(10ms대). 사용자가 입력을 정하는 기능에서는 최악의 경우를 테스트로 만들어 측정해야 한다.

### 문장 예시

> 졸업작품인 AI 헬스케어 챗봇의 위기 신호 감지를 개선하기 위해 트라이, 실패 링크, Aho-Corasick 검색을 C로 직접 구현해 검증했습니다. 최악 입력에서 단순한 방법이 37초 걸리던 검색을 5ms로 줄였고, 메모리도 측정해 배열 기반 트라이가 최악의 경우 약 1GB를 쓴다는 것을 확인하고 이를 근거로 서비스에는 해시맵 기반 구조를 선택했습니다.
